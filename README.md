# Trading Platform

A simulated brokerage and stock-trading platform built with Go.

The project is a backend-focused learning project designed around a production-style architecture. It includes a REST API, MariaDB, NATS JetStream, asynchronous workers, an order-matching engine, an outbox pattern, and real market-price data from Twelve Data.

> **Important:** This is a simulation. It does not execute real trades or use real money. Real market data is used only to provide current market prices for the simulated trading environment.

> **Important:** Since this is a backend project, website's design was generated by AI so you might encounter bugs related to front-end.

> **Important:** Twelve Data requires specific plan to track prices of other stocks, by dafault it works only with AAPL!
## Features

### Authentication
- User registration and login
- JWT authentication
- UUID-based user IDs
- Password hashing

### Accounts
- Account creation
- Balance, reserved balance and available balance
- Account information

### Instruments
- Stock/instrument management
- Lookup by ID or symbol
- Instrument listing

### Orders
- BUY and SELL orders
- LIMIT and MARKET orders
- Order creation, listing, cancellation, status and filled quantities
- MARKET BUY `max_cost` safety limit

### Matching engine
A dedicated matching worker processes order-created events asynchronously.

It supports:
- Compatible BUY/SELL LIMIT matching
- Price/time ordering
- Partial fills
- Execution creation
- Position updates
- Account balance updates
- Reserved funds and positions
- MARKET BUY `max_cost`
- Cancellation of unfillable market orders
- Transactional database updates

All trading is simulated.

### Positions and executions
Users can view current holdings, including instrument, quantity, reserved quantity and average price. Executions are persisted and exposed through the API.

### Real market data
The market-data worker receives current prices from Twelve Data and publishes them to NATS. The API consumes those prices into an in-memory `PriceStore` which the simulated market-order logic uses.

### Components

- **API** (`cmd/api`) — HTTP API, authentication, accounts, orders, positions, executions, health/readiness and Swagger.
- **Matching worker** (`cmd/matching-worker`) — consumes order-created events and runs the matching engine.
- **Outbox worker** (`cmd/outbox-worker`) — publishes database outbox events to NATS.
- **Market-data worker** (`cmd/market-data-worker`) — receives Twelve Data prices and publishes them to NATS.
- **PriceStore** (`internal/marketdata`) — keeps the latest known market price in API memory.

## Environment variables

Create `.env` from `.env.example`:

```env
DB_ROOT_PASSWORD=change-me
DB_USER=trading
DB_PASSWORD=change-me
DB_NAME=trading

JWT_SECRET=change-me-to-a-long-random-secret

NATS_URL=nats://localhost:4222

TWELVE_DATA_API_KEY=your-twelve-data-key
MARKET_DATA_SYMBOLS=AAPL
```

`.env` contains secrets and must not be committed. Docker Compose automatically reads the local `.env` file and substitutes `${...}` values in `compose.yaml`.

## Running with Docker Compose

Start the full development stack:

```bash
docker compose up --build
```

This starts:

- MariaDB
- NATS with JetStream
- Goose migration service
- API
- matching worker
- outbox worker
- market-data worker

Check services:

```bash
docker compose ps
```

Logs:

```bash
docker compose logs -f
docker compose logs -f api
docker compose logs -f matching-worker
docker compose logs -f outbox-worker
docker compose logs -f market-data-worker
```

Stop:

```bash
docker compose down
```

Remove development volumes as well:

```bash
docker compose down -v
```

> `docker compose down -v` deletes the MariaDB and NATS development data.

## Trading model

### LIMIT orders

A LIMIT BUY executes only at or below its limit price. A LIMIT SELL executes only at or above its limit price.

Funds and positions are reserved while pending. When execution occurs, the appropriate reservation is converted into spent funds or sold position and unused reservation is released when applicable.

### MARKET orders

MARKET orders use the latest available real market price from `PriceStore`.

For MARKET BUY orders, `max_cost` limits the amount that may be spent. For example, if one share costs `$200` and `max_cost` is `$250`, the order can execute. If the current price is `$300`, the order cannot execute and its reserved funds are released.

## Market-data limitations

`PriceStore` is intentionally in-memory. After an API restart it is empty until new NATS market-price messages arrive.

Market prices are not used as historical database records in this project.

## NATS and JetStream

NATS is used for asynchronous communication. JetStream provides durable delivery and explicit acknowledgements for order processing.

Important subjects include:

```text
orders.created
market.price.<SYMBOL>
```

A successfully processed order is acknowledged by the matching consumer. Failed processing can result in redelivery.

## Outbox pattern

Order events are persisted as database outbox records before publication.
This prevents the database state and event publication from becoming an unsafe dual write.

## Graceful shutdown

All application processes support graceful shutdown via normal termination signals.

- API shuts down its HTTP server and dependencies.
- Matching worker stops consuming new JetStream messages and closes resources.
- Outbox worker stops processing new events and closes resources.
- Market-data worker closes its Twelve Data WebSocket and NATS connection.

## Health and readiness

### Liveness

```http
GET /health
```

Returns:

```json
{"status":"ok"}
```

### Readiness

```http
GET /ready
```

Checks required API dependencies such as MariaDB and NATS. Dependency failure results in HTTP `503`.

## Docker architecture

The Dockerfile builds separate binaries for:

```text
api
matching-worker
outbox-worker
market-data-worker
```

A separate migrator target contains Goose and the migrations.

Inside Docker, services communicate using Compose service names rather than `localhost`:

```text
api -> mariadb:3306
api -> nats:4222
matching-worker -> mariadb:3306
matching-worker -> nats:4222
outbox-worker -> mariadb:3306
outbox-worker -> nats:4222
market-data-worker -> nats:4222
```
